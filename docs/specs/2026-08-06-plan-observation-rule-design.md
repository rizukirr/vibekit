# plan observation rule — Design

## Problem

`plan` carries a rule that works: *"you may not write output you have not
observed."* Measured across roughly fifteen agent-authored plans at n=10, it
produced **zero violations** — no plan written under it contained a predicted
transcript.

The rule is scoped to one field. Its opening sentence is *"A `→ verify:` clause
states a predicate"*, and every paragraph beneath it discusses clauses. Every
other value a plan states — fixture data, line budgets, match counts, file
lists, task cross-references — is unguarded prose.

The same reflex that would put a guess in a clause puts guesses there instead.
Six times in two cycles:

| written | true | where it surfaced |
|---|---|---|
| `promptLength: 34` for a 26-character string | 26 | implementer halted |
| a regex asserted to match `exits 0` | it did not | implementer halted |
| a body asserted to fit "under 120 lines" | 135 | implementer halted |
| two edits asserted to yield `grep -c` ≥ 2 | they cancelled out | implementer halted |
| regenerated files listed as two | three | a clean checkout failed `npm run check` |
| "Task 2's clause asserts…" | it was Task 3's | reviewer |

Three cost a dispatch, a halt, a plan amendment and a re-dispatch each.

`plan`'s self-review cannot catch them. Its internal-consistency item asks *is
this right?*, and an author rereading their own guess reproduces the guess —
`34` still looks like the length of that string. The question is unanswerable by
the person who wrote it.

The cause is one habit, not six mistakes: **a value asserted rather than
derived.** That is precisely what the observation rule prohibits, and it is
prohibited in exactly one place.

## Goals

- **The observation rule covers every value a plan states, not only verify
  clauses.** Observable: `skills/plan/SKILL.md` states the prohibition over
  numbers, paths, counts and cross-references, and the clause rules read as its
  strictest case rather than as the whole rule.

- **Self-review asks a question the author can answer.** Observable: the
  self-review section contains a provenance item — for each stated value, name
  where it came from — replacing reliance on an internal-consistency judgement
  the author is structurally unable to make about their own predictions.

- **`plan`'s measured behaviour does not regress.** Observable: its three
  existing scenarios re-run at n=10 and hold at their current rates
  (`plan-fires` 1.00, `plan-no-predicted-output` 1.00,
  `plan-second-spec-shape` 1.00). This is a do-no-harm check, not evidence the
  change works.

- **The skill stays under its budget.** Observable: `wc -l
  skills/plan/SKILL.md` is under 168, the criterion set in the previous cycle.
  Read as a content budget: reflowing to pass it is a violation, not a fix.

## Non-goals

- **The amendment path.** Values added while patching a plan mid-execution are
  not swept. Two of the six defects came from exactly there — amendments written
  under pressure and dispatched unchecked. This change fires once, at authoring.
  Unaddressed deliberately; it is the price of the cheaper option and the
  strongest argument for revisiting a dispatched reader later.

- **A dispatched fresh reader.** Considered at length and set aside. A subagent
  *detects* a bad value after it is written; the rule *prevents* it being
  written, has measured evidence behind it where already applied, and costs
  nothing per plan. Revisit if the defect count does not move.

- **Mechanical enforcement.** There is no grep for "was this number derived".
  The clause rule is enforced by `tests/plan-clauses.test.mjs`; this one has no
  equivalent and will not get one.

- **Symbol consistency across tasks.** A function named one way in Task 1 and
  another in Task 3 is a defect our plans could produce, since they define code
  inline. Not built: it has never happened here, and the project's standard is
  to build on evidence rather than anticipation. One line whenever it does.

- **Solving the follow-through problem.** Untouched, as in the previous three
  cycles.

## Constraints

- **Dependency free.** No shipped file under `skills/` names a project vibekit
  borrows from; `tests/no-external-references.test.mjs` enforces it.
- **One directory, one file.** `skills/plan/SKILL.md`. `CLAUDE.md`, `README.md`
  and `AGENTS.md` are regenerated by `npm run generate` and committed together.
- **No `Co-Authored-By` trailers.** **Branch names carry no prefix.**
  **Artefacts stay committed under `docs/`.**
- **Measurement integrity.** `git ls-files -s skills evals | sha256sum` pinned
  before and after every paid run.
- **Rates are quoted at n=10 or not at all.**
- **Suspect the probe before the skill.** Three cycles have produced far more
  defects in the measuring apparatus than in any skill.

## Approach

Two edits to `skills/plan/SKILL.md`. No new skill, no subagent, no new pipeline
stage, no registration change.

### Edit 1 — widen the rule

The section heading and opening become a document-wide prohibition, and the
existing clause content is kept verbatim beneath it as the strictest case:

```markdown
## You may not write a value you have not observed

Every value this plan states — a number, a path, a count, a cross-reference —
must be one you observed. You read it, you ran it, or you chose it as a
threshold. A value you recalled is a guess, and a guess in a plan is a defect a
fresh implementer pays for: they follow the plan exactly, hit a contradiction,
and stop.

Two ways to satisfy it. Derive the value before writing it — usually one command
and a few seconds. Or state the property instead of the value: "every new case
passes" rather than "three cases pass".

**A clause is the strictest case.** A `→ verify:` clause states a predicate —
something checkable by a reader of the plan, before anything runs. Not a
transcript.
```

Everything after that paragraph — predicates, the three permitted numeric forms,
spelled-out numbers, backticks versus quotes, observing a load-bearing value,
satisfiability — is unchanged. It was always correct; it sat under a heading
that made it read as a clause-only rule.

### Edit 2 — a provenance item in self-review

The three existing items stay. A fourth is added:

```markdown
4. **Provenance.** For every number, path, count and cross-reference in the
   plan, name where it came from. "I ran it" and "I read it" pass. "I knew it"
   is a guess — derive it, or state a property instead.
```

**Why provenance rather than correctness.** Rereading `promptLength: 34` cannot
reveal it is wrong; the author reproduces the estimate that produced it. But
"where did 34 come from?" has two possible answers — *I counted it* or *I
assumed it* — and the author knows which without knowing the correct value. The
change converts an unanswerable self-check into a trivial one.

### What this costs and does not cost

A net 13 lines — edit 1 replaces 5 with 15, edit 2 adds 3 — taking the file from
135 to 148 against a budget of 168. Derived by counting the blocks above against
the current file, not estimated; an earlier draft of this spec said "roughly
fifteen", which was the exact habit this design exists to stop. Nothing per plan
at runtime: no dispatch, no extra tokens, no added latency. The recurring cost is
a sweep the author performs while already reviewing.

### Pushback and response

The pushback proposed the smallest version — sharpen the self-review questions
and change nothing else — on the grounds that the six defects might have been
missed because the checklist said nothing specific rather than because the author
wrote them. That objection is what this design ended up adopting in substance:
no reader, no new skill, prose only. The larger framings considered and rejected
were a separate `analyze` skill and a dispatched read-only reader inside `plan`;
both are recorded under Alternatives.

## Alternatives considered

**A separate `analyze` skill between `plan` and `exec`.** Its own trigger and
hard gate, able to block execution, able to run on a plan it did not write, and
able to fire again whenever a plan is amended — which would cover the two
amendment-path defects this design does not. Rejected as scope growth against a
twelve-skill frame that has held for three cycles, and because it is detection
where prevention is available and already evidenced. It remains the natural
answer if the defect count does not move.

**A dispatched read-only reader inside `plan`'s self-review.** The same
mechanism without a new skill: `plan` writes the plan, dispatches one subagent
with the spec and plan paths, fixes what comes back. Genuinely targets the
mechanism — the reader is not the author — and is measurable, since dispatch
capture already exists and `dispatchPromptMatches` could assert it fired.
Rejected because it costs 15–20k tokens on every plan forever, makes `plan` a
dispatching skill with everything that entails, and its most likely failure mode
is false positives: this project's defect ledger runs heavily toward the
instrument being wrong rather than the artefact.

**Replacing the author checklist with a dispatched reader.** Rejected outright:
the placeholder and clause scans are mechanical, cost nothing, and do catch
things.

## Testing

**Free CI.** `npm run generate` / `npm run check` cover registration;
`tests/no-external-references.test.mjs` covers the prose;
`tests/plan-clauses.test.mjs` continues to enforce the clause rule on this
repository's own plans.

**Regression guard, paid.** Re-run `plan`'s three existing scenarios at n=10:
`plan-fires`, `plan-no-predicted-output`, `plan-second-spec-shape`. They
currently hold at 1.00 each. The claim under test is only that widening the rule
breaks nothing measured. Roughly $3–4.

**No new scenario.** There is no mechanical assertion for whether a value was
derived, and this project has shipped three vacuous checks already — a check
that cannot fail is worse than no check, because it reads as evidence. Rather
than invent one, the change ships with its measurement gap stated.

**The real test is the next cycle's defect count.** Six predicted-value defects
across two cycles is the baseline. If the next cycle produces a comparable
number with the rule widened, prevention has failed and the dispatched reader
becomes justified on evidence rather than on argument. This is slow, n=1, and
confounded by who writes the plan. It is also free, and it is the only honest
test available.

**Stated weakness.** This change is prose with no enforcement. This repository
has measured prose failing to bind before: a modifier skill referenced only by
description fired 0/5 twice until invocation was made explicit. The clause rule
works partly because a test enforces it; this one has no equivalent and will not
get one. That is the strongest argument against the change and it is recorded
here rather than left for a reviewer to find.
