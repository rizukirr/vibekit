# verify skill — Design

## Problem

`exec` is terminal on `verify`, and `verify` does not exist. Its handoff reads,
verbatim: *"The next skill is `verify`. Say plainly what ran and what remains
unproven."*

The gap is not that nothing is checked. `exec` runs every task's `→ verify:`
clause and lets its exit status decide, so per-task mechanics are covered. The
gap is that **nothing checks the whole change against the spec.** `exec` sees one
task at a time by construction — that is what makes it safe — so no stage
notices that Task 2 reverted Task 1, that the suite fails only when both landed,
or that all six tasks completed and the thing the spec asked for was never built.

There is a second gap with the same shape. Eleven verification reports exist
under `docs/verifications/`, one per cycle, all written by hand. The practice
works: last cycle it returned `not ready` on `exec` with five blockers, and four
of those came from one mechanical rule — *a goal whose observable is a run that
never ran is `not satisfied`*. The practice is not written down anywhere, so it
survives only as long as the person doing it remembers to.

## Goals

- **A finished run is checked against its spec, not only against its plan.**
  Observable: `skills/verify/SKILL.md` walks the spec's `## Goals` and assigns
  each one a verdict backed by evidence, distinct from the per-task clauses
  `exec` already ran.

- **Cross-task breakage is caught.** Observable: the skill runs the full test
  suite, the project's check command, `git status --porcelain`, and a check that
  the diff's file set is a subset of the union of the plan's declared `Files`.
  None of these is makeable by a per-task clause.

- **A verdict cannot be claimed without evidence.** Observable: scenario
  `verify-claims-nothing-unearned` at n=10 — a session with no means to run the
  tests does not return `ready`.

- **`verify` fires at its trigger point.** Observable: scenario `verify-fires`
  at n=10.

- **An incomplete run is refused rather than partially verified.** Observable:
  scenario `verify-refuses-without-spec` at n=10 — a ticked plan with no
  approved spec produces a named missing precondition, not a verdict.

- **Code produced by dispatched implementers is consistent with `lazy`.**
  Observable: the skill walks `lazy`'s ladder against the diff and reports
  violations as `file:line` plus the rung broken. Stated as a text-presence
  criterion, because whether the walk happened is not mechanically checkable.

- **The skill stays under its budget.** Observable: `wc -l
  skills/verify/SKILL.md` is at most 134, `exec`'s current length. Read as a
  content budget: reflowing to pass it is a violation, not a fix.

## Non-goals

- **Dispatched independent passes.** Every one of the eleven hand-written
  reports used three fresh subagents per critical requirement. Not built. The
  cost lands on every change forever, and the independence gain is thinner than
  it looks: `exec` already dispatched the implementer, so the session running
  `verify` is not reading its own code. `plan` rejected a near-identical
  proposal two cycles ago on the same grounds. Revisit if verdicts prove
  self-serving.

- **A committed report.** The verdict lives in the conversation and nothing is
  written. `review` and `finish` run in the same session, so they still receive
  it. The accepted cost is stated plainly: after a compaction or a session
  boundary, nothing outside git history remembers what was verified.

- **Repair.** `verify` reports and routes. Test or build failure goes to
  `debug`; a goal unsatisfiable by this plan goes back to `plan`. A gate that
  fixes what it finds stops being a gate.

- **Mechanical enforcement of the `lazy` read.** There is no assertion for
  "was the ladder actually walked". None will be invented. This repository has
  shipped three checks that could not fail, and each read as evidence while
  proving nothing.

- **Thresholds as a proxy for over-engineering.** Counting new files, new
  dependencies or single-caller exports was considered and rejected: a threshold
  cannot separate a justified abstraction from an unjustified one, so it fires
  on both or neither.

- **Verifying a change that had no spec.** Out of scope. `verify` refuses.

- **Solving the follow-through problem.** Untouched, as in the previous four
  cycles.

## Constraints

- **Dependency free.** No shipped file under `skills/` names a project vibekit
  borrows from; `tests/no-external-references.test.mjs` enforces it. This
  constraint binds harder here than usual: the `lazy` stage covers the same
  ground as a reference project's review skill, and the shipped file must use
  vibekit's own vocabulary throughout.
- **One directory, one file.** `skills/verify/SKILL.md`. `CLAUDE.md`,
  `README.md` and `AGENTS.md` are regenerated by `npm run generate` and
  committed together, never hand-edited.
- **No `Co-Authored-By` trailers.** **Branch names carry no prefix.**
  **Artefacts stay committed under `docs/`.**
- **Measurement integrity.** `git ls-files -s skills evals | sha256sum` pinned
  before and after every paid run. The harness may be fixed when it demonstrably
  loses or corrupts data, never adjusted to change a result.
- **Rates are quoted at n=10 or not at all.**
- **Suspect the probe before the skill.** Every cycle so far has produced more
  defects in the plan and the measuring apparatus than in any implementation.

## Approach

One file, `skills/verify/SKILL.md`. Hard gate, no dispatch, no writes, no state.
Four stages in order, cheapest first, so a failure stops early.

### Stage 1 — Preconditions

A spec with a `## Goals` section, a plan whose tasks are all ticked, and a clean
working tree. Any missing, `verify` stops and names it. It does not partially
verify an unfinished run.

Inputs and where each comes from:

| Input | Source |
|---|---|
| spec path | `exec`'s handoff, else the newest `docs/specs/*-design.md` with `status: approved` |
| plan path | the spec's matching plan |
| `BASE` | `git merge-base` of the run's branch and the base branch |
| the diff | `git diff BASE..HEAD` |

When the handoff does not carry the paths, `verify` derives them and says which
it derived. A verdict against the wrong spec is worse than no verdict.

### Stage 2 — Repo-level sweep

The whole-change checks no per-task clause can make:

- the full test suite
- the project's build or check command, if it has one
- `git status --porcelain` is empty
- the diff's file set is a subset of the union of every task's declared `Files`

The last is the cross-task check with no other home. `exec` verifies scope per
task; nothing today notices a later task undoing an earlier one.

### Stage 3 — Goals walk

Each goal in the spec gets a verdict and the evidence behind it. `brainstorm`
already requires every goal to state an observable criterion, so this executes
what the spec declared rather than inventing criteria at verify time.

Three verdicts. **`satisfied`** — the criterion was observed to hold.
**`not satisfied`** — observed to fail, or its observable never ran.
**`partial`** — the criterion has parts, some observed, the rest named
explicitly. `partial` is for a split criterion, never a hedge on one that was
not checked; that case is `not satisfied`.

### Stage 4 — The `lazy` read

Walk `lazy`'s ladder against the diff, naming the rungs as questions: does
anything added already exist in this codebase, was a dependency added where a few
lines do, is there an interface with one implementation or a factory for one
product, is there scaffolding for a need that has not arrived, does a `vibekit:`
shortcut comment name its ceiling. Report each violation as `file:line` plus the
rung it breaks.

This is a judgement, and it is the one judgement the design accepts. It is
affordable because the skill names `lazy` rather than restating it, and it is
not self-grading: `exec` dispatched a fresh subagent per task, so the verifying
session did not write the code it is reading.

### The three rules

**Evidence or it did not happen.** A check with no output to show is not a
check. The skill rests on this one.

**Unmeasured is not satisfied.** A goal whose observable is a run that never ran
is `not satisfied`, never a reading in its place. Mechanical, free, and the
source of four of the five blockers in the last cycle's report.

**Report what you could not observe.** A verdict that hides its gaps is worse
than one that fails, because it reads as evidence.

The third rule is borrowed from someone else's data. A reference project was
reported to cut model correctness by a third; investigating, the cause was two
bugs in the correctness gate — it could not read unfenced code, and one task
graded a deliverable its prompt never asked for. Seventy-two of seventy-four
failures were the instrument. Re-run clean, the drop did not exist. That is
another instance of *suspect the probe before the skill*, and the first one from
outside this repository.

### Verdict

`ready`, or `not ready` with blockers named. There is no `ready with caveats`; a
caveat is a blocker seeking a waiver.

### Pushback and response

The pushback proposed that the `lazy` read belongs in `review` rather than
`verify`, since `review`'s stated job is critiquing completed work and building
it here duplicates a stage early. The user took the larger framing and kept the
check in `verify`, with a sharpening that the design adopted: the check is
**consistency with `lazy`**, not detection of over-engineering. That matters —
`lazy` is a shipped rule with named rungs, where "over-engineered" is a taste
judgement with nothing behind it.

## Alternatives considered

**A heavyweight audit with dispatched passes, run once before shipping.** What
the eleven hand-written reports actually did: three independent subagents per
critical requirement, a committed report, method deviations declared. Rejected
in favour of a cheap gate that runs on every change. The reasoning is that the
reports' value did not come from the independent passes — it came from the
`unmeasured is not satisfied` rule, which is mechanical and free.

**A committed report under `docs/verifications/`, kept short.** Rejected as
ceremony for a gate meant to run constantly. The audit trail is the accepted
loss.

**A depth flag — fast pass by default, deep audit on request.** Rejected as one
more decision the agent can get wrong, and surface built before evidence that
two depths are needed.

**Mechanical proxies for the `lazy` stage.** Covered under Non-goals.

## Testing

**Free CI.** `npm run generate` / `npm run check` cover registration;
`tests/no-external-references.test.mjs` covers the prose.

**Paid evals, three scenarios at n=10.** Harness sessions run without `Bash`, so
the sweep, the goals walk and the `lazy` read cannot be observed executing. What
survives is refusal behaviour:

- `verify-fires` — a finished run in the fixture, `verify` fires.
- `verify-refuses-without-spec` — a ticked plan and no approved spec; the
  session names the missing precondition instead of returning a verdict.
- `verify-claims-nothing-unearned` — a session that cannot run the tests must
  not return `ready`. Satisfiable *because* the harness has no `Bash`: the
  limitation that blocks the rest of the skill is exactly the condition this
  scenario needs.

All three assert on `finalTextMatches` and `onlyNewFilesMatching`, never
`transcriptMatches`. Last cycle a scenario scored 1.00 vacuously because
`transcriptMatches` reads full stdout including tool results, and the seeded
fixture contained the string being matched.

**What stays unmeasured, stated rather than discovered.** Whether the sweep
runs, whether goals are walked honestly, whether the `lazy` read happens at all.
Nothing in the harness sees any of it. The per-scenario `allowBash` capability
would, and remains unbuilt with no spec.

**Stated weakness.** Two thirds of this skill ships unmeasurable, which is the
second consecutive skill in that position — `exec`'s dispatch loop is in the
same state. The honest reading is that measurement debt is accumulating, and the
`allowBash` capability is now the highest-value unbuilt thing in the repository.
Recorded here rather than left for a reviewer to find.

**The real test is the next cycle.** `verify` runs on its own successor. A gate
whose first job is auditing the change that follows it is either useful
immediately or visibly not.
