# Plugin submission package: Implementation plan

**Spec:** docs/specs/2026-10-08-plugin-submission-design.md

**Goal:** Produce a repeatable, locally validated, hook-free skills ZIP and accurate upload instructions for the OpenAI plugin directory.

**Architecture:** A dedicated Node command stages an allowlist of submission files, validates the staged package, and invokes the installed native ZIP tool. Dedicated listing metadata and an SVG icon are independent of the existing runtime emitters. Submission-only skill adaptations happen in staging, leaving shared installed skills unchanged.

## Global constraints

- Preserve existing installation packages and runtime behavior.
- Generate the submission package separately from the existing installation artifacts.
- Use existing dependencies or native tools before introducing a dependency.
- Exclude secrets, Git internals, lifecycle hooks, and unrelated development files from the archive.
- Preserve existing unrelated working tree changes, including the previously present docs files.
- Do not invent publisher details, public policy URLs, or reviewer credentials. Report any required information that the repository cannot supply.
- Verify current OpenAI submission metadata and asset requirements before implementation.

## Observed inputs and decisions

The current configuration is `vibekit.config.json`. `package.json` is generated by `runtimes/core.mjs` from its `npm.scripts` object. Shared skill discovery and frontmatter validation live in `lib/model.mjs` and `lib/frontmatter.mjs`. The existing Codex manifest declares hooks, so copying it unmodified is unsuitable. `/usr/bin/zip` is installed in this workspace. Use native `zip` and `unzip` for archive creation and independent inspection, with a clear prerequisite error if either is unavailable.

Official requirements were read at https://developers.openai.com/plugins/deploy/submission on 2026-10-08. A Codex manifest requires `name`, `version`, `description`, `author.name`, `skills`, and `interface`. Listing fields include `displayName`, `shortDescription`, `longDescription`, `developerName`, `category`, `capabilities`, `logo`, and `composerIcon`. Icons may be SVG, must be square and at least 48 by 48, and must be at most 5 MiB. Choose a 128 by 128 SVG icon. Skills-only submissions do not require MCP review cases or all four MCP listing URLs. Lifecycle hooks and app references cannot be submitted.

Choose `dist/openai/vibekit-<current-version>.zip` as the artifact path. Keep archives ignored. Choose `submission/README.md` as the maintained upload guide and `submission/interface.json` as the dedicated listing metadata. Package only the Codex manifest, discovered skills and their resources, generated trigger table documentation, icon, license, and submission guide. Do not include the portable root manifest, which would introduce another ingestion format.

### Step 2: Implement staging and validation

Use `buildModel` for discovery and input validation, and the current configuration for package identity. Construct the submission manifest from explicit supported fields rather than copying the hook-bearing runtime manifest. Add `extensions.com.openai.onboardingSkill` pointing to the packaged startup skill. Copy discovered skill directories, refusing symbolic links and paths outside the source tree. Generate a packaged trigger table using `lib/table.mjs` and include `AGENTS.md` as a referenced resource. Do not claim a plugin-root AGENTS file loads automatically.

Adapt only the staged startup skill. Replace the CLAUDE-specific trigger table reference with a resolvable relative path to the packaged AGENTS file. Replace the mandatory `Skill` tool instruction with Codex-compatible skill invocation guidance and a file-reading fallback when a dedicated invocation tool is unavailable. Explain explicit user activation and that lifecycle startup hooks are absent. Fail clearly if expected source text no longer matches, preventing silent drift. Audit other staged instructions for concrete runtime dependencies and document unsupported capabilities rather than claiming they were tested.

Validate required identity fields, semantic version shape, listing string limits, capability entries, HTTPS website URL, declared icon paths and SVG dimensions and size. Require nonempty discovered skills and packaged bootstrap skill. Validate literal local Markdown resource links in the staged skills and declared manifest resources. Distinguish illustrative future document paths from actual bundled resource dependencies. Refuse traversal, absolute paths, hooks, app references, secrets and unexpected staged entries. Local validation is targeted package validation, not a claim to reproduce OpenAI's review scanner.

Keep the package builder testable with a supplied source root and output destination. Use a fresh temporary staging directory and a temporary ZIP. Invoke tools with argument arrays and no shell interpolation. Validate before creating the archive, and rename the successfully completed temporary archive to its final destination. Clean up only directories created by this invocation. A failure must leave any preexisting destination archive intact and return a nonzero status with a useful error.

### Step 3: Wire the command and guide

Add this script to `vibekit.config.json` under `npm.scripts`, then regenerate:

Add `/dist/` to `.gitignore`. Add a short README link to `submission/README.md`. Include clean Codex smoke-test steps and state whether they were actually run. Explain that local archive validation does not imply portal acceptance. Do not add fabricated policy URLs or MCP review materials. Provide the guide inside the archive as `README.md`.
