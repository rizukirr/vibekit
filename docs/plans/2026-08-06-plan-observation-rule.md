# plan observation rule Implementation Plan

> **For executing agents:** implement this plan task-by-task. Each step uses checkbox (`- [ ]`) syntax. Do not skip steps. Do not batch commits across tasks.

**Goal:** Widen `plan`'s observation rule from verify clauses to every value a plan states, and replace an unanswerable self-review question with an answerable one.

**Architecture:** Two verbatim edits to `skills/plan/SKILL.md`. No new file, no subagent, no registration change. The skill's frontmatter is untouched, so `npm run generate` produces no changes to the generated docs — `npm run check` is run anyway to prove it.

**Spec:** `docs/specs/2026-08-06-plan-observation-rule-design.md` (status: approved).

**Authored under the rule it proposes:** every count in this plan was derived by running a command against the current file, not estimated. `observed` appears on 1 line today; `provenance` on 0; self-review has 3 numbered items; the file is 135 lines.

## Premortem

**Hidden assumptions:**
- The plan assumes editing body prose leaves the generated docs untouched, because the frontmatter `description` is unchanged. The previous cycle confirmed this twice: two body-only edits to `skills/exec/SKILL.md` produced no generated-file changes and `npm run check` stayed green. Both tasks run `npm run check` regardless, so a wrong assumption fails the task rather than surfacing later.
- The plan assumes `grep -c observed` reaches 2 after edit 1. Derived, not estimated: the file has 1 such line now (the heading), the replacement keeps the heading and adds `must be one you observed`. The later phrase `observes it` does not match `observed` and is unaffected.

**Irreversible / risky steps:**
- none — two prose edits to one tracked file, each revertible with `git revert`. No paid run happens in this plan.

**Spec-misalignment:**
- The spec's goal "self-review asks a question the author can answer" is observable only as text presence. No mechanical check can confirm an author actually performed a provenance sweep. The spec states this gap explicitly rather than implying coverage; this plan inherits it and does not invent a proxy assertion.

**Verify-clause weakness:**
- `npm test` alone would pass without either edit landing, since no test asserts the skill's prose. Each task's clause therefore also greps for a token the edit introduces, so a task that changed nothing fails.
- A grep count could be satisfied by text added anywhere in the file. Accepted: the plan-compliance review reads the diff, and the edits are verbatim replacements at named anchors.

### Task 1: Widen the observation rule → verify: `npm run check` exits 0, `npm test` exits 0, `grep -c observed skills/plan/SKILL.md` finds at least 2 matches, and `wc -l < skills/plan/SKILL.md` is under 168

**Files:**
- Modify: `skills/plan/SKILL.md`

- [x] **Step 1: Replace the heading and opening paragraph**

In `skills/plan/SKILL.md`, replace exactly this:

```markdown
## You may not write output you have not observed

A `→ verify:` clause states a predicate — something checkable by a reader of the
plan, before anything runs. Not a transcript.
```

with exactly this:

```markdown
## You may not write a value you have not observed

Every value this plan states — a number, a path, a count, a cross-reference —
must be one you observed. You read it, you ran it, or you chose it as a
threshold. A value you recalled is a guess, and a guess in a plan is a defect a
fresh implementer pays for: they follow the plan exactly, hit a contradiction,
and stop.

Two ways to satisfy it. Derive the value before writing it — usually one command
and a few seconds. Or state the property instead of the value: "every new case
passes" rather than "three cases pass".

**A clause is the strictest case.** A `→ verify:` clause states a predicate —
something checkable by a reader of the plan, before anything runs. Not a
transcript.
```

Change nothing else in the file. Every paragraph below this point stays exactly as it is.

- [x] **Step 3: Check the derived properties**

- [x] **Step 4: Commit**
